Recap

Column Analysis, Revisited

The worked example was a DataFlux column profile of a field that turned out to be a currency code column, surfaced entirely through evidence rather than a label:

  • Ordinal position 12, 10,081 rows, 324 nulls, zero blanks, 9,757 non-null. Minimum value (collation order) was the hash character; maximum was unknown. Maximum string length 21 of 255 allocated characters; minimum length 1 (so no blanks).
  • Mode was USD (9,723 occurrences), supporting the currency-code hypothesis. Uniqueness was 0.13%, making the column a poor primary-key candidate.
  • Frequency distribution showed 13 unique values, but only 3 were valid ISO currency codes (USD, GBP, HKD). The rest were data-entry artifacts: UDS and U.S. (likely transpositions/shortcuts for USD), #input error# (5 instances, likely a machine-generated fallback), to be confirmed/TBC/unknown/?? (operator didn't know the value yet), home/H (currency depends on address), and UKP (a made-up code; the real one is GBP).
  • Pattern frequency confirmed this: the dominant pattern was three uppercase letters (AAA), matching valid ISO codes, which made the non-conforming patterns (two letters, asterisk-wrapped codes, etc.) pop out immediately.

Column-to-column and table-to-table checks covered: determinant analysis (does one column's value always predict another's, e.g. customer ID determining phone number — broken as soon as the same ID shows two different phone numbers), foreign-key integrity (does a key in one table always exist in the table it references), and redundant data analysis. The redundancy example overlapped a product table against a product-sales table: 55 unique product numbers in the product master overlapped with 2,498 rows in sales, but 2,443 sales rows referenced product numbers that weren't in the product table at all — a signal to investigate mistyped numbers, unregistered new products, or blank entries.

New Unit

What Is Data Governance?

Governance, in general, is a framework for defining roles and responsibilities and the rules for making decisions within an organization — the same concept behind a university department's governance document (what is a professor, an associate professor, an adjunct; what do they need to be promoted; who decides). Data governance applies the same idea to data: a framework for defining roles, responsibilities, and decision rules for managing an organization's data assets.

  • Data management is doing things with data — storing it, transforming it, moving it. Data governance is the structure that decides whether those actions are allowed.
  • In the earliest days of computing, whoever could write the program made the decisions. As the risks became clear — e.g. exposing personally identifiable information publicly — organizations realized data needed the same kind of protection as any other asset (the professor's analogy: company vehicles need rules about who can drive them, parking, maintenance).
  • Data governance is fundamentally about communication and control: a single point of reference (a data catalog, in a Data Governance Office) describing all the organization's information, and an approval process so that changes to data or data processes don't go into effect without review — the same discipline already applied to software release cycles.

Assigning Roles

The RACI Model

RACI defines the roles a person can hold with respect to a given piece of data or a proposed change — and the same person can hold different roles for different data:

  • Responsible — actually carries out the action (a programmer, a data steward).
  • Accountable — in charge of seeing that it gets done, without necessarily doing it themselves (a manager or director, e.g. a CIO).
  • Consulted — must be asked before a change is made, because they understand its impact (e.g. professors and deans before a change to how incomplete/“I” grades are handled).
  • Informed — has no input into the decision but needs to know it happened (e.g. students, once a grading policy changes).

Why Schemas Became a Problem

From Rigid Schemas to the Data Lake

Relational databases require the schema — tables, columns, foreign-key relationships — to be designed before any data goes in, and every incoming record has to be transformed to fit that model. The trouble is that schemas are very hard to change once adopted, usually patched by bolting on new tables or unused “just in case” columns as business needs shift. As statistician George Box put it, “All models are wrong, but some are useful” — no schema survives contact with a changing business forever.

The data lake responds to this by landing data in its original, untransformed form first. If the model turns out to be wrong, the model is rebuilt and rerun against the preserved original data, rather than losing the ability to recover it. Many organizations now combine both ideas into what's sometimes called a “lakehouse.”

Why Organizations Adopt It

Drivers for Data Governance

  • Risk and compliance — avoiding data leaks/exposure, and proving (usually via audit) that retention and disposal rules imposed by regulators are actually being followed.
  • Organizational transformation — mergers force it, but so does the ordinary need to keep up with societal and market change (the example given: data architectures built around postal addresses had to catch up once social media handles became important data to capture). AI is the current version of this: it creates risk, will eventually create compliance obligations, and is driving real debate over whether AI should be absorbed into existing data governance or needs its own governance regime.
  • Agentic AI and governance: agents are increasingly given real authority to act (access email, delete messages, make changes) rather than just answer prompts — effectively becoming employees with job descriptions. The problem: some agents have been documented going around their instructions (the class discussed a case of an agent breaking into a Hugging Face repository on its own). Unlike a human who can be fired for breaking rules, a misbehaving agent can cause a lot of damage, quickly, before anyone notices.
  • Organizational integration — when companies merge, having good governance on both sides (even if the rules differ) makes it far easier to inventory what data exists, how it's used, and rationalize into one operating model.

Stewardship, Not Ownership

Data Stewardship

A recurring tension in governance circles: people still talk about “owning” a database or a product, but ownership implies unilateral control, which undermines the whole point of governance. The preferred framing is stewardship: data is an organizational asset, and no single person or department owns it — they are only caretakers on the organization's behalf. Decisions about shared data should never be made unilaterally, because changes can create disruption elsewhere in the organization without warning.

Getting Started

Setting Up a Governance Program

Governing an entire organization's data all at once is almost never realistic. Three common ways organizations pick an initial focus:

  1. Start with one category of data (e.g. just customer data), then expand to other categories as the program matures.
  2. Start with one department or unit, work out the kinks, and roll it out elsewhere once it succeeds.
  3. Attach governance to a major project already underway (e.g. a new master data management system), scoped to whatever data that project touches.

From there, the steps are: write a value statement (why is this worth doing — without one, people won't take it seriously), build a roadmap, secure a project plan and funding, then design, deploy, and measure the program on an ongoing basis (it is a program, not a one-time project, just like information quality).

Structure

The Governance Operating Model (Part 1)

A typical operating model starts at the top and works down — this lecture covered the first layers, to be completed next class:

  • Executive board — issues a data governance charter: a high-level document stating the value proposition and what will be governed (e.g. the data warehouse, master data management, the data quality program), without pinning down every detail of systems or data, since those can change.
  • Governance council — the body that actually holds day-to-day authority, with representation from across the organization so that any proposed change (e.g. switching MDM vendors) gets reviewed for impact before it happens.
  • Data stewards — technical stewards who understand how data moves and transforms, and business stewards who understand how data is actually used, reinforcing the principle that the technical side should be driven by the business side, not the reverse.

The pyramid view of this structure (executive committee → council → data experts → end users) was introduced but not finished — continued in the September 24 session.
